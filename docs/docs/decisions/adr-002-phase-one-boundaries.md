# ADR-002: GitHub Plugin Phase One Boundaries

## Status

Accepted — 2026-07-28

## Amendment (2026-07-28)

Several decisions below turned out to be generic rather than GitHub-specific and were **promoted to
the plugin contract** by `SubZeroDev.PluginContract/adr/ADR-003`. They are left in place here as the
record of what was decided and why; the contract is now authoritative for them.

Promoted: the exit-code table, secrets from the environment only, serialization and atomic
replacement, schema-version compatibility, `null` over optional, configuration precedence, and
logging levels.

Still owned here: repository scope and filters, identity on GitHub's numeric ID, capability-flag
mapping, commit count via the `Link` header, the request budget, summary selection, and portfolio
overrides.

The argument-parsing decision is now split: the contract requires strict per-command option
validation, while the choice of `node:util` `parseArgs` to achieve it stays an implementation detail
of this plugin.

## Amendment (2026-07-29)

The "Documentation layout" decision below is superseded. `setup-llm/docs/` and the pre-rename `setup/`
path belonged to the pre-split monorepo this plugin was scaffolded inside. `SubZeroDev.Plugins.GitHub`
is now its own repository: the specification and the ADRs live under `docs/docs/reference/` and
`docs/docs/decisions/`, published at `plugins-github.subzerodev.com`. The reasoning for the decision —
one path, no duplicate copies — is unaffected and is why the same rule now applies to this repository's
own layout.

## Context

Version 1.0 of the specification left several boundaries open and, in a few
places, answered the same question twice with different answers. The primary goal
claimed owned and contributed repositories while the discovery section limited
Phase One to owned ones; authentication permitted a token in a configuration file
without saying how it would be protected; the API-call budget was undefined; and
the output shape, portfolio metadata, and commit-count questions were still
listed as open while downstream work needed them settled.

Those gaps are cheap to close now and expensive later. Output shape determines
schemas, serializers, cache keys, and atomic-write granularity. Repository
identity determines whether incremental synchronization can exist at all. Both
would force a re-cut of the published schema if decided after the fact.

## Decisions

### Scope

Phase One discovers only repositories owned by the authenticated user.
Contributed repositories, organization repositories, and forks-of-others remain
the eventual goal but need a different discovery strategy and a much larger
request budget. Forks are excluded by default and configurable. Archived,
disabled, and template repositories are included by default and flagged.

### Repository identity

A repository is keyed on GitHub's immutable numeric ID, namespaced by provider.
`owner/name` is mutable metadata and never a key.

Keyed on `owner/name`, a rename or transfer is indistinguishable from a deletion
followed by an addition, so the cache would discard history and re-fetch on every
rename. Every future provider must supply an equivalently stable identifier.

### Authentication

The token is read from an environment variable, `GITHUB_TOKEN` by default. The
configuration file may name a different variable; it may never carry a token
value, and the configuration schema must be incapable of representing one.

A schema that cannot hold a token is a stronger guarantee than a rule against
logging one, because it also rules out the token reaching the cache, the exported
documents, an error message, or a crash dump.

### Output

Output is consolidated: one canonical document per concern, covering every
project. Per-repository files are future scope.

All top-level documents share one schema version. A reader accepts the same major
version and rejects anything else with an actionable error. Phase One ships no
migration mechanism — below `1.0.0`, an incompatible document is regenerated by
re-running `export`. Absent values serialize as `null` rather than being omitted,
which keeps output byte-stable and avoids the friction between Zod's `.optional()`
and the `exactOptionalPropertyTypes` compiler flag.

### Statistics

Commit count is collected by requesting a single-item commit page and reading the
last page number from the `Link` header, at one request per repository. The
original objection to commit count was its cost; at one request that objection no
longer holds. It is null when the header is absent, as for an empty repository.

Capability flags are mapped only where GitHub exposes them directly. There is no
`has_releases` and no `has_packages`, so neither is collected, and neither is
synthesized by probing an endpoint and inferring a flag.

Issue counts exclude pull requests, because GitHub's `open_issues_count` includes
both. Closed counts come from the Search API, which uses a separate rate-limit
bucket and is eventually consistent, so a disagreement between consecutive syncs
of unchanged data is expected rather than a change. Contributor lists carry a
truncation flag, because GitHub caps them and omits anonymous contributors.

Any statistic that cannot be collected is null with a diagnostic, never zero. A
repository with no commits and a repository whose commit count could not be read
are different facts and must not serialize identically.

### Summary selection

"Largest" is the greatest repository size, "most active" the latest `pushedAt`,
"newest" and "oldest" the extremes of `createdAt`. Every selection breaks ties by
ascending repository identity. Undefined selections would let the summary change
between runs over unchanged data, which contradicts the determinism principle.

### Request budget

Default concurrency is 4 in-flight requests, configurable. A full uncached
collection costs no more than 10 requests per repository. Against the 5000/hour
primary limit, the run warns at 50% consumed and stops cleanly at 90%, reporting
partial success. Search API usage stays at or below 20 per minute.

A `304` response does not consume primary quota, so an unchanged resync should
approach zero consumption rather than merely fewer requests.

### Cache and atomic replacement

The cache atomically replaces current state; historical snapshots are future
scope. Replacement writes to staging and then renames each file onto its live
path. Directory replacement is not used: it is not atomic on Windows and fails
when the destination exists, and Windows is a supported platform.

Partial failure preserves the last valid cached data for whatever failed, exits
`4`, and records diagnostics naming the affected repositories.

### Portfolio metadata

Projects carry an optional, provider-independent `custom` object for data that
does not exist in GitHub. It is separate from the repository model so provider
data and hand-authored data never become indistinguishable and a resync cannot
overwrite hand-authored values. It also gives the deferred AI-summary and asset
questions somewhere to land without a schema change.

### CLI

Argument parsing stays on `node:util` `parseArgs`, using two stages: global
options up to the command token, then the remainder against that command's own
option table. A single global table would let every command accept every other
command's flags, which is the opposite of the strict validation required. No CLI
parser dependency is added.

Exit codes are `0` success, `2` usage or validation error, `3` operational
failure, `4` partial synchronization, `5` authentication or authorization error,
and `6` rate-limited before completion. `1` is deliberately unused, because
Node.js returns it for an uncaught exception and leaving it unassigned keeps a
crash distinguishable from a handled failure.

### Logging

Specification levels map onto Pino as Information → `info`, Warning → `warn`,
Error → `error`, Debug → `debug`, and Verbose → `trace`.

### Documentation layout

The specification and ADRs live under `setup-llm/docs/`. The pre-rename `setup/`
path is not written to; duplicate copies were tracked at both paths for a period
and had to be removed, and a second copy silently drifts the moment either is
edited.

## Consequences

- The specification, the implementation plan, and `TODO-next.md` can be made to
  agree, and disagreement becomes a defect rather than an ambiguity.
- Contracts can be defined without waiting on open questions, so the schema is
  cut once.
- Some collected data is explicitly approximate — truncated contributor lists,
  eventually-consistent closed counts — and says so in the model rather than
  presenting an approximation as exact.
- Deferring organization and contributed repositories means the primary goal is
  only half met in Phase One. This is stated in the specification rather than
  left for a reader to discover.
- Rejecting configuration-file tokens diverges from specification 1.0, which
  permitted them. The specification is updated rather than the decision relaxed.
- No migration path exists for exported documents before `1.0.0`. Consumers
  regenerate instead of upgrading, and the documentation must say so rather than
  implying otherwise.
